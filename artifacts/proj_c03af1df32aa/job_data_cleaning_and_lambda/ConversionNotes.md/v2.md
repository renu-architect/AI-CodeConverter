## Conversion Notes

### Fix 1 — Performance: removed `df.count()` calls from `filter_null_provider_ids` (lines 163–172, MEDIUM severity)

**Root cause:** The original implementation called `df.count()` before filtering and `filtered_df.count()` after filtering. Both are Spark *actions* that force a full dataset scan purely to populate a log message. On large inputs this doubles (or triples, counting the downstream action that eventually materialises the pipeline) the number of full scans with zero business logic benefit.

**Change made:** Both `count()` calls and the associated `before`/`after` integer variables were removed entirely. The log statement was replaced with a single informational message that requires no materialisation:

```python
logger.info(
    "NULL provider ID filter applied: rows with null provider id removed."
)
filtered_df: DataFrame = df.where(col("provider id").isNotNull())
return filtered_df
```

The docstring was updated to document the deliberate omission and to provide a copy-paste pattern for teams that have a hard auditing requirement (cache → count before → filter → count after → unpersist), so the trade-off is transparent to future maintainers.

---

### Fix 2 — Error handling: `count()` calls were not wrapped in try/except (lines 163–172, LOW severity)

**Root cause:** Because `df.count()` is a Spark action, any transient I/O error on a source partition during the count scan would surface as an uncontextualised Spark exception with no indication of which pipeline stage failed. The count calls were not wrapped in a try/except, so the stage label would be lost.

**Change made:** This issue is resolved as a direct consequence of Fix 1 — by removing both `count()` calls entirely, there is no longer any Spark action in `filter_null_provider_ids` that could raise an I/O exception during the filter step. The only remaining expression is a lazy `DataFrame.where(...)` transformation, which defers execution to the next downstream action and is covered by the top-level `try/except Exception` block in `run()`, which logs the stage context via `exc_info=True` before re-raising.

No additional try/except wrapper was introduced inside `filter_null_provider_ids` because wrapping a lazy transformation (not an action) would provide no meaningful error-isolation benefit; the exception can only be raised when the DAG is executed, which happens inside `run()` where it is already handled.
