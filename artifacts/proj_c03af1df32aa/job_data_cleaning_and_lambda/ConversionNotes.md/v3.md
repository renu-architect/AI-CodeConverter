## Conversion Notes

### Fix 1 — `synapse_compatibility` (HIGH) · Lines 21–21: conditional `mssparkutils` import

**Problem:** The original `from notebookutils import mssparkutils` is an unconditional import that raises `ModuleNotFoundError` when the file is executed as a Synapse Spark Job Definition (`.py`), because the `notebookutils` alias is only pre-installed in the Synapse *Notebook* kernel. Additionally, the `# noqa: F401` comment was suppressing a linter warning about an unused import, masking the dead-weight dependency.

**Fix applied:** Replaced the single unconditional import with a three-level `try/except ImportError` guard:
1. First attempts `from notebookutils import mssparkutils` (Synapse Notebook context).
2. Falls back to `import mssparkutils` (Synapse Spark Job Definition context).
3. Sets `mssparkutils = None` if neither is available (local / unit-test context).

The `# noqa: F401` suppression was removed. The docblock comment above the import block explains the intent and notes that the import is retained for future secret-retrieval or filesystem operations rather than being silently dead code.

### Fix 2 — `performance` (MEDIUM) · Lines 130–131: `getNumPartitions()` on the hot path + missing repartition

**Problem (part A — `getNumPartitions` log):** `df.rdd.getNumPartitions()` was called unconditionally inside `read_source()` and its result logged at `INFO` level on every run. While the call itself does not trigger a full Spark action, materialising the RDD layer and logging on every execution adds unnecessary DAG overhead in the read path.

**Fix applied (part A):** The `logger.info(...)` call containing `getNumPartitions()` was replaced with a `DEBUG`-level guard:
```python
if logger.isEnabledFor(logging.DEBUG):
    logger.debug("Source read complete. Inferred partition count: %d", df.rdd.getNumPartitions())
```
This means the partition count is only computed and logged when the logger is explicitly set to `DEBUG`, keeping the `INFO`-level hot path clean.

**Problem (part B — missing repartition):** There was no explicit repartition anywhere in the pipeline. On a Synapse Spark pool with many executors, the default partition count from a CSV read can be suboptimal for the subsequent `withColumn` chain and Parquet write, causing either too many small output files or insufficient parallelism.

**Fix applied (part B):** An explicit repartition step was added in `run()` immediately after `read_source()`:
```python
target_partitions: int = spark.sparkContext.defaultParallelism
raw_df = raw_df.repartition(target_partitions)
```
`spark.sparkContext.defaultParallelism` reflects the total number of executor cores available on the Synapse pool, making the partition count self-adapting to pool size without hardcoding. The `run()` docstring was updated to document this as step 2 of the pipeline. A comment in the code notes that a fixed value can be substituted if the pool node count is known and stable.

### Fix 3 — `transformations` (LOW) · Lines 253–255: redundant `cast(LongType())` in `build_nested_schema()`

**Problem:** Inside `build_nested_schema()`, the provider struct contained `col('provider id').cast(LongType()).alias('id')`. The `provider id` column was already cast to `LongType` in `resolve_provider_id()` and filtered for nulls in `filter_null_provider_ids()`. The redundant cast added a no-op expression to the physical plan and could mislead future maintainers into thinking the first cast was insufficient.

**Fix applied:** Removed the redundant `.cast(LongType())` from the provider struct expression:
```python
# already cast to LongType in resolve_provider_id()
col("provider id").alias("id"),
```
An inline comment was added to make the intent explicit and prevent the cast from being re-introduced during future maintenance. The physical plan is now clean, and the code is self-documenting about the upstream type contract.
