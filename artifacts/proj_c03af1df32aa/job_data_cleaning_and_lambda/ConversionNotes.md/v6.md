## Conversion Notes

### Fix 1 — `resolve_provider_zip_code()`: Remove row-drop filter (HIGH severity, business_logic)

**Root cause:** The original implementation applied `.where(col('provider zip code').isNotNull())` after casting to `LongType`, silently dropping any row whose ZIP code could not be cast. The original Glue job never performed this filter — non-numeric ZIPs became `null` in the output struct field `provider.zip` but the row was retained.

**Changes made:**
- Removed the `filtered_df = resolved_df.where(col("provider zip code").isNotNull())` line entirely.
- `resolve_provider_zip_code()` now returns `resolved_df` directly — the cast is applied, non-numeric values become `null`, but no rows are dropped.
- Updated the function docstring to explicitly document the intentional deviation from the provider-id pattern, explain why rows are retained, and describe the stakeholder sign-off path if dropping bad ZIPs ever becomes a genuine business requirement.
- Updated the `run()` docstring step 5 to reflect the corrected behaviour.
- Updated the `build_nested_schema()` docstring to note that `provider.zip` may be `null` for records with non-numeric ZIPs, matching original Glue `apply_mapping` semantics.
- Updated the module-level docstring bullet point for zip code handling.

### Fix 2 — `resolve_provider_zip_code()`: Remove `df.count()` materialisation (MEDIUM severity, transformations)

**Root cause:** The original implementation called `df.where(...).count()` before applying the cast, triggering a full dataset scan with no DataFrame caching — an anti-pattern explicitly identified in the `filter_null_provider_ids()` docstring.

**Changes made:**
- Removed the `invalid_zip_count = df.where(...).count()` block and the surrounding `if/else` branch entirely.
- Replaced with a single unconditional `logger.warning(...)` call that surfaces the data-quality notice at plan-construction time without any Spark action. This provides observability (visible in Synapse Monitor / Log Analytics) with zero additional DAG cost.
- The docstring `.. note::` block explicitly explains why `df.count()` is not used and cross-references the `cache()/unpersist()` pattern from `filter_null_provider_ids()` for teams that need pre-write auditing.

### Fix 3 — `_strip_leading_char()`: Document null-handling deviation (LOW severity, business_logic)

**Root cause:** The behavioural change from the original lambda (raises `TypeError` on `None`) to the new implementation (returns `None`, Spark casts to `null` double) was undocumented, making it untraceable during validation.

**Changes made:**
- Added an explicit `.. note::` block in the `_strip_leading_char()` docstring labelled **"Deviation from original Glue job (LOW severity — intentional improvement)"** that states: the original lambda raises `TypeError` on `None`; this implementation returns `None` which Spark casts to `null` double; no row is lost; downstream null handling is unchanged; this is an intentional improvement requiring no stakeholder sign-off.
- Added a top-level `DEVIATIONS FROM ORIGINAL GLUE JOB` section in the module docstring that registers both the `_strip_leading_char` deviation (item 1) and the `resolve_provider_zip_code` row-retention behaviour (item 2) in a single, easily auditable location.
