## Detailed Findings

### Check 1 & 4 — Business Logic / Transformations (Score: 82–88)

**Finding 1 — Zip Code Null-Filter Is a Behavioural Addition (HIGH)**

The original Glue job never filters on `provider zip code`. It reads the column as `long`, applies `resolveChoice` only to `provider id`, filters only on `provider id IS NOT NULL`, and then passes `provider zip code` directly into `apply_mapping` as `long → long`. Non-numeric ZIP values in the original would silently become `null` in the output struct field `provider.zip` — they would **not** cause row removal.

The converted code introduces `resolve_provider_zip_code()` which casts the ZIP column and then **drops rows** where the cast produces null. This is a net-new row-drop that has no equivalent in the original job. For any source data containing non-numeric ZIP codes, the converted job will produce fewer output rows than the original. This is a correctness divergence, not just an enhancement.

**Finding 2 — UDF Null-Safety Is a Minor Semantic Shift (LOW)**

The original lambda `lambda x: x[1:]` would raise `TypeError` at runtime if `x` is `None`. The converted `_strip_leading_char` guards against `None` and returns `None` instead. This is a safe improvement but is a behavioural change: the original would fail the task on null monetary values; the converted code silently produces a null `double` in the output. This is acceptable but should be documented as an intentional deviation.

**Finding 3 — Repartition Before Zip Resolution (LOW)**

`repartition(defaultParallelism)` is called after the provider-id filter but before `resolve_provider_zip_code`. If zip-code filtering drops a significant number of rows, the repartition shuffle is partially wasted. This is a minor inefficiency, not a correctness issue.

---

### Check 7 — Performance (Score: 78)

**Finding 4 — Zip Count Materialisation Path (MEDIUM)**

The omitted 36 lines of `resolve_provider_zip_code` contain a `df.count()` call (inferred from the docstring: *"Count the newly introduced nulls and emit a WARNING log"*). If this count is unconditional, it triggers a full dataset scan mid-pipeline with no caching, adding latency proportional to dataset size. The docstring for `filter_null_provider_ids` explicitly warns against this pattern and recommends `cache()`/`unpersist()` if counting is required. The zip function should follow the same guidance or use an accumulator pattern.

---

## Summary

The migration is **functionally sound for the happy path** — all Glue APIs are removed, the core transformations (UDF, struct nesting, type casting, null filtering on provider ID) are correctly reproduced, and the output schema matches exactly. The primary concern is the **zip code row-drop behaviour**, which is a silent correctness divergence from the original job. All other issues are minor or advisory.
