## Detailed Findings

### 1. Business Intent (Weight: 30% | Score: 97)

**Assessment: ✅ PASS**

All five logical stages of the original Glue job are preserved in correct sequential order:

| Stage | Original Glue Mechanism | Synapse Implementation | Preserved |
|---|---|---|---|
| Type resolution | `resolveChoice(cast:long)` on `provider id` | `resolve_provider_id()` → `col().cast(LongType())` | ✅ |
| Null filtering | `filter` on resolved DynamicFrame | `filter_null_provider_ids()` → `where(isNotNull())` | ✅ |
| Currency strip | `lambda x: x[1:]` UDF | `_strip_leading_char()` UDF with null guard | ✅ |
| Schema restructure | `apply_mapping` with nested paths | `build_nested_schema()` → `select(struct(...))` | ✅ |
| Parquet write | `write_dynamic_frame.from_options(format="parquet")` | `write_parquet()` → `df.write.mode("overwrite").parquet()` | ✅ |

**Deviations:**

- **Null-safe UDF (LOW severity — intentional improvement):** The original `lambda x: x[1:]` raises `TypeError` on `None` input, which would fail the Spark task at runtime. The converted `_strip_leading_char` returns `None` instead, which Spark casts to `null` double downstream. No row is lost; this is a correctness improvement, not a semantic deviation. Deviation is documented in the module docstring and the function docstring.
- **`provider zip code` row-retention behaviour (NEUTRAL — correctly preserved):** The original Glue `apply_mapping` retained rows with non-numeric ZIP codes, producing `null` in `provider.zip`. The converted `resolve_provider_zip_code` matches this behaviour exactly: rows are retained, a WARNING is logged, and `provider.zip` is `null`. This is correctly documented as a non-deviation.

**Deduction: -3** for the absence of explicit stakeholder sign-off documentation on the UDF null-guard deviation, even though the deviation is low-severity and technically correct.

### 5. Performance Impact (Weight: 10% | Score: 88)

**Assessment: ✅ PASS**

| Concern | Assessment | Verdict |
|---|---|---|
| Post-filter repartition | Correctly placed after `filter_null_provider_ids` — shuffle operates only on retained rows | ✅ Correct |
| No `df.count()` on hot path | Confirmed — row-count materialisation explicitly avoided with documented rationale | ✅ Correct |
| Debug-only partition count | `logger.isEnabledFor(logging.DEBUG)` guard prevents `getNumPartitions()` overhead in production | ✅ Correct |
| `when/otherwise` in `resolve_provider_zip_code` | Adds one full column scan for ZIP observability; acceptable given the dataset size and the value of the WARNING log | ⚠️ Acceptable |
| UDF serialisation overhead | Python UDF (`_strip_leading_char`) applied to three columns sequentially — three separate UDF invocations per row | ⚠️ Minor |
| Repartition target | `spark.sparkContext.defaultParallelism` — correct for Synapse pool alignment; may over-partition on small datasets | ⚠️ Minor |
| No caching between steps | Pipeline is linear with no repeated DataFrame references — caching is correctly omitted | ✅ Correct |
| `overwrite` mode | Matches original unconditional write; no partition-level overwrite risk since no partitioning is specified | ✅ Correct |

**Deduction: -12** for three minor performance concerns:
1. **Three sequential Python UDF calls (-5):** `strip_currency_symbols` applies the UDF three times in separate `withColumn` calls. A single `select` with three UDF expressions would allow Spark to pipeline the UDF invocations more efficiently, though the practical impact is small on typical Medicare dataset sizes.
2. **`when/otherwise` full column scan (-4):** The zip-code observability pattern adds a column scan. On very large datasets this is non-trivial; a sampling-based approach would be more scalable.
3. **`defaultParallelism` repartition target (-3):** This is correct for CPU-bound workloads but may produce suboptimal file sizes for Parquet output if the pool has high parallelism and the dataset is small. A target-partition calculation based on estimated data volume would be more robust.
