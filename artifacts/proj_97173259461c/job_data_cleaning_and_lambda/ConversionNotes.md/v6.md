## Conversion Notes

### Fix Applied: `null_filter_semantics` (lines 148–160, severity HIGH)

**Root cause**

The original `filter_nulls()` implementation used `df.dropna(how="any")`, which drops every row that contains a null in *any* column. The source Glue job only applied the predicate `WHERE \`provider id\` IS NOT NULL`. Fields such as `hospital referral region description` and `total discharges` are nullable in the source data and were never excluded by the original job. The blanket `dropna` was therefore silently discarding valid records, producing a smaller and potentially biased output dataset that violated the original job's output contract.

**Change made**

Replaced `df.dropna(how="any")` with a single targeted column filter:

```python
return df.filter(col("provider id").isNotNull())
```

This exactly replicates the original Glue `WHERE \`provider id\` IS NOT NULL` predicate. Rows with nulls in any other column are retained, matching the original pipeline's output contract.

**Pipeline ordering preserved**

`filter_nulls()` is still called *before* `resolve_provider_id()` in `main()`, which matches the original Glue pipeline order (`Filter → resolveChoice → Map → apply_mapping`). This means:

1. The null check runs on the raw `StringType` `provider id` column, exactly as the original Glue `Filter` transform did.
2. Any non-numeric string values in `provider id` that survive the filter are subsequently converted to `null` by the `LongType` cast inside `resolve_provider_id()`, faithfully replicating the `cast:long` behaviour of Glue's `resolveChoice`.

**Docstring updated**

The `filter_nulls()` docstring was rewritten to document the targeted-filter semantics, explain why `dropna(how='any')` was incorrect, and describe the pipeline ordering rationale. All other functions and the `main()` docstring were updated to reflect the corrected description of step 2.
