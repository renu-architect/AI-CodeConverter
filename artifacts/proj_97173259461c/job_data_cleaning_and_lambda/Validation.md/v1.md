### 2. Transformation Accuracy (95/100)

**Confirmed Correct:**

| Original Glue Transform | Converted Implementation | Semantic Equivalence |
|---|---|---|
| `resolveChoice(specs=[('provider id','cast:long')])` | `col("provider id").cast(LongType())` in `resolve_provider_id()` | ✅ Exact: non-castable values → null, matching Glue cast:long behaviour |
| `Filter(WHERE \`provider id\` IS NOT NULL)` | `df.filter(col("provider id").isNotNull())` in `filter_nulls()` | ✅ Exact: targeted single-column null filter, not `dropna()` |
| `Map(lambda x: x[1:])` on three monetary columns | `regexp_replace(col(...), r"^\$", "")` wrapped in `when().otherwise(lit(None))` | ✅ Behaviourally equivalent for `$`-prefixed values; null-safe improvement |
| `apply_mapping` (rename + cast + nest) | `df.select(struct(...).alias(...))` in `nest_and_cast()` | ✅ All field renames, type casts, and struct nesting reproduced |
| `datasink` Parquet write | `df.write.mode("overwrite").parquet(path)` in `write_output()` | ✅ Equivalent; `overwrite` mode adds idempotency not present in original |

**Pipeline Ordering Verified:**
- `resolve_provider_id()` is called before `filter_nulls()` in `main()`, correctly matching the original Glue order: `resolveChoice → Filter`. This is critical: non-numeric `provider id` strings are cast to null first, then excluded by the filter. Reversing this order would allow corrupt string values to pass the `isNotNull()` check and produce null longs in the output.

**Minor Observation:**
- `regexp_replace(r"^\$", "")` is strictly safer than `x[1:]` for values not beginning with `$`. This is a documented improvement, not a regression. The original lambda would silently corrupt such values; the converted code leaves them unchanged. Downstream consumers relying on the original truncation behaviour for malformed data should be notified, but this is an edge case not present in the known source data.

| Glue Data Catalog (`payments.medicare`) | Direct ADLS Gen2 path read | ✅ |

**Synapse-Native Patterns Verified:**
- `SparkSession` pre-initialised by Synapse runtime; `get_spark()` correctly uses `getOrCreate()`.
- Storage account injected via `spark.conf.get("spark.job.storage_account")` rather than hardcoded, with fast-fail `assert` on placeholder value.
- `__main__` guard present with CLI argument parsing for `--enable-row-counts`, supporting both Notebook and Spark Job Definition execution modes.
- All imports are standard PySpark; no AWS-specific libraries (`awsglue`, `boto3`) remain.

**Minor Observation:**
- The `assert` statement on `_STORAGE_ACCOUNT` executes at module import time. In Synapse notebooks, if the Spark conf is not set before the import cell executes, this raises `AssertionError` before `main()` is called — which is the intended fast-fail behaviour. However, `assert` statements are disabled when Python runs with the `-O` (optimise) flag. A production hardening option would be to replace the `assert` with an explicit `if`/`raise ValueError(...)` guard. This is a low-risk observation given that Synapse Spark pools do not typically run with `-O`, but it is worth noting for strict production environments.
- The `try/except` block around the initial `SparkSession.builder.getOrCreate()` for conf reading (lines 44–52) silently falls back to the placeholder value on exception, which then triggers the `assert`. This is correct behaviour but the two-step pattern (try/except → assert) could be simplified to a single `if`/`raise` block for clarity.

### 5. Performance Impact (87/100)

**Confirmed Correct:**
- `count()` is gated behind `enable_row_counts: bool = False`, defaulting to off in production. This avoids an extra full distributed scan that would double I/O cost on the post-filter dataset.
- The conditional `count()` is placed after `filter_nulls()`, meaning it scans the smaller post-filter dataset rather than the full raw input. This is the correct placement.
- Explicit `SOURCE_SCHEMA` on CSV read avoids `inferSchema=True`, which requires a full two-pass scan of the source data. This is a meaningful performance improvement over a naive migration.
- No intermediate `cache()` or `persist()` calls are present, which is correct: the DAG is simple enough (single linear chain, no branching) that caching would add memory pressure without benefit.
- No unnecessary shuffles are introduced. All transformations are narrow (`withColumn`, `filter`, `select`) with no joins, aggregations, or repartitions.
- `write.mode("overwrite").parquet(path)` is a single-pass write with no intermediate materialisation.

**Minor Observation:**
- The `get_spark()` function calls `spark.sparkContext.setLogLevel("WARN")` on every invocation. Since `get_spark()` is called once in `main()`, this is not a performance concern in practice, but if `get_spark()` were called multiple times (e.g. in unit tests), repeated `setLogLevel` calls are harmless but redundant. This is a negligible observation.
- No explicit `repartition()` or `coalesce()` is applied before the Parquet write. For very large Medicare datasets this could result in many small Parquet files. However, since the original Glue job also did not specify partitioning, this matches the original behaviour and is not a regression.
